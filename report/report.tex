\section{Introduction}

\subsection{Business objectives}

Internet-of-Things devices have become a vast and largely unmonitored attack
surface. Compromised cameras, routers and digital video recorders are
weaponised into botnets such as \emph{Mirai}, \emph{Hide-and-Seek} and
\emph{Torii}, generating distributed denial-of-service traffic, port scans and
command-and-control flows that share a network with legitimate device
traffic. The economic and operational damage of these botnets motivates the
deployment of automated network-traffic classification at the scale of an
entire ISP or data centre.

The business objective of this project is to demonstrate, on a representative
real-world dataset, that:
\begin{enumerate}[leftmargin=2em]
    \item Raw Zeek connection logs from heterogeneous IoT captures can be
    ingested, stored and queried at the scale of tens of millions of rows
    using a standard Hadoop/Spark stack.
    \item A small set of statistical insights derived from the data can
    already separate benign traffic from several distinct attack behaviours.
    \item A distributed multiclass classifier trained on the same warehouse
    can flag malicious connections with very high accuracy, providing a
    practical first-line filter for a security operations team.
\end{enumerate}

The deliverable is a fully reproducible pipeline (a single \texttt{main.sh}
that re-creates every artefact from the original CSV input), a public Apache
Superset dashboard, and this report.

The dataset is a hand-picked subset of the
\textbf{Aposemat IoT-23} corpus (Stratosphere Lab, Czech Technical

network traffic recorded over several years. Each capture contains a Zeek
\texttt{conn.log} file describing every observed network connection, with
both binary (\texttt{Benign}/\texttt{Malicious}) and detailed multi-class

\section{Data Preparation}

\subsection{Relational model and ER diagram}

The relational model in PostgreSQL consists of two tables connected by a
single foreign key. \texttt{captures} is the dimensional reference for the
twelve IoT-23 captures; \texttt{network\_connections} is the fact-style table
that holds every parsed Zeek connection record.

\centering

\subsection{Hive warehouse}

The Hive database \texttt{team30\_projectdb} contains two physical layouts
optimised for different access patterns:

\begin{itemize}[leftmargin=2em]
    \item \texttt{captures\_bucketed} --- \texttt{CLUSTERED BY (capture\_id) INTO 4 BUCKETS},
    Parquet, used as the join dimension table.
    \item \texttt{network\_connections\_part} --- \texttt{PARTITIONED BY (label)},
    Parquet. Because every analytical query and every ML feature scan filters
    by label, partitioning at this column lets the Tez engine prune to a
    fraction of the data on every access.
\end{itemize}

The warehouse is materialised by \texttt{sql/db.hql}, run on the Tez engine
with dynamic partitioning enabled:

\begin{lstlisting}
SET hive.execution.engine=tez;
SET hive.exec.dynamic.partition=true;
SET hive.exec.dynamic.partition.mode=nonstrict;
SET hive.enforce.bucketing=true;

INSERT OVERWRITE TABLE network_connections_part PARTITION (label)
SELECT connection_id, capture_id, CAST(ts AS TIMESTAMP), uid,
       id_orig_h, id_orig_p, id_resp_h, id_resp_p,
       proto, service, duration, orig_bytes, resp_bytes,
       conn_state, local_orig, local_resp, missed_bytes, history,
       orig_pkts, orig_ip_bytes, resp_pkts, resp_ip_bytes,
       tunnel_parents, detailed_label, label
FROM network_connections_ext;
\end{lstlisting}

\subsection{Insight 4 --- Per-capture maliciousness ratio}

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth]{img/q4.jpg}
\caption{Total flows and malicious ratio per capture.}
\end{figure}

\textbf{Interpretation.} Capture-level distribution is strongly bimodal:

\subsection{Insight 5 --- Connection state per label}

\textbf{Interpretation.} A SYN-only flow (\texttt{conn\_state = S0}) is the
universal signature in this dataset. Even benign IoT traffic is dominated

\texttt{RSTOS0} (the originator gets a RST after SYN). C\&C flows show a

% ====================== ML MODELING ======================
\section{ML Modeling}

\subsection{Feature extraction and preprocessing}

\texttt{scripts/ml\_data\_preparation.py} builds a single PySpark
\texttt{Pipeline} over the Hive partition. The pipeline is fitted only on
the training fold to prevent leakage:

\begin{enumerate}[leftmargin=2em]
    \item \textbf{Cyclical time encoding.} A custom
    \texttt{CyclicalTimeTransformer} extracts year, month, day, hour,
    minute, second from \texttt{ts} and produces sine/cosine pairs for the
    five periodic components. This prevents the model from inferring a
    spurious linear ordering across time wrap-arounds.
    \item \textbf{Imputation.} \texttt{tunnel\_parents} is dropped
    (constant null). Strings are filled with \texttt{"unknown"}; numeric
    nulls become 0; boolean nulls become \texttt{False}.
    \item \textbf{Categorical encoding.}
    \texttt{StringIndexer + OneHotEncoder} for \texttt{proto},
    \texttt{service}, \texttt{conn\_state}, \texttt{history}.
    \item \textbf{Feature selection.} A \texttt{ChiSqSelector(fpr=0.1)}
    over the categorical block keeps only label-correlated dummies.
    \item \textbf{Assembly + scaling.} \texttt{VectorAssembler} concatenates
    numeric features, time encodings and the ChiSq-selected categoricals;
    \texttt{StandardScaler(withMean=False, withStd=True)} produces the final
    \texttt{features} column.
\end{enumerate}

The label column is handled by a \texttt{StringIndexer} fitted on the same
training fold. The split is $60\%/40\%$, seed 42, and the train/test
DataFrames are persisted as Parquet on HDFS so that training and evaluation
read from a stable on-disk artefact.

\subsection{Models and hyperparameter tuning}

Both models are wrapped in a Spark
\texttt{CrossValidator(numFolds=2, parallelism=3)} optimising the multiclass
\texttt{f1} metric. Each \texttt{spark-submit} runs on YARN with 6 executors
$\times$ 3 cores $\times$ 6 GB. The training set is
\texttt{persist(MEMORY\_AND\_DISK)} so that CV folds can amortise the I/O.

shallow tree splits dominate a globally-linear model. Predictions are
persisted to HDFS as CSV so that the evaluator is decoupled from training
and can be re-run without retraining.

    \item[D. Top targets (Insight 6).] Port histograms per non-Benign label;
    the bar for port 23 dominates and is annotated as the Mirai entry
    point.
    \item[E. Capture strata (Insight 4).] Per-capture maliciousness ratio,
    rendered as a bar chart that exposes the bimodal capture-level
    distribution.
    \item[F. Model performance.] Comparison panel rendered from
    \texttt{evaluation.csv}, showing accuracy / precision / recall / F1 for
    both models side by side.
\end{description}

\subsection{Findings}

The dashboard surfaces three findings that are not obvious from the raw
data:
\begin{enumerate}[leftmargin=2em]
    \item \textbf{Class skew is non-degenerate.} Four classes carry the
    bulk of the data and three rare classes carry diagnostic signal.
    Treating the task as multiclass (and not binary) preserves that
    diagnostic value.
    \item \textbf{The attack surface is concentrated.} Port 23 alone
    accounts for more than 7M malicious flows. A single network policy that
    rate-limits inbound Telnet on the IoT subnet would have cut the bulk
    of the malicious volume in this corpus.
    \item \textbf{A simple model is enough --- if non-linear.} A
    distributed Random Forest with only four hyperparameter combinations
    explored reaches $F_1 = 0.998$ at this feature set. The same problem is
    near-unsolvable for a multinomial linear model, which is the strongest
    practical argument for keeping a tree ensemble in the production
    classifier.
\end{enumerate}

% ====================== CONCLUSION ======================
\section{Conclusion}

\subsection{Summary}

This project delivered a fully reproducible end-to-end big-data pipeline
that ingests 25M Zeek connection records from the Aposemat IoT-23 corpus,
stores them in a partitioned Hive warehouse on HDFS, runs seven HiveQL EDA
queries on Tez, trains and cross-validates two distributed Spark ML models
on YARN, and presents the results in a public Apache Superset dashboard.
The Random Forest model achieves $F_1 = 0.998$ across seven classes on a
held-out test set of approximately 10M rows. Every artefact in the
\texttt{output/} folder is regenerable from a single \texttt{main.sh}.

\subsection{Reflections on own work}

The team's role split worked well: the data engineer owned ingestion and
the Hive warehouse layout, the ML specialist owned the Spark pipeline and
hyperparameter grid, the data scientist owned EDA and dashboard
storytelling, and the tester/technical writer documented every stage and
ran the reproducibility checks. The reproducibility contract --- ``one
\texttt{main.sh}, every stage idempotent'' --- was particularly valuable
because it forced us to clean up intermediate state at the start of each
script rather than relying on a previous run's artefacts.

\subsection{Challenges and difficulties}

\begin{itemize}[leftmargin=2em]
    \item \textbf{Type coercion at ingestion.} The raw Zeek CSVs use
    sentinel \texttt{-} values for missing fields and float-formatted
    integers (\texttt{1234.0}). The PostgreSQL transformation insert had to
    handle both via \texttt{NULLIF} + \texttt{REGEXP\_REPLACE} before
    casting --- a single missed regex caused a full reload.
    \item \textbf{Hive partitioning vs.\ skew.} Label-partitioning
    \texttt{network\_connections\_part} produced one tiny partition
    (\texttt{Malicious FileDownload}, 3 rows) and four very large ones.
    This is acceptable for analytical scans but costs us shuffle balance
    in Spark; the workaround was \texttt{repartition(18)} after reading.
    \item \textbf{LR convergence.} The multinomial Logistic Regression
    converged to a near-trivial solution under the given feature set ---
    not a bug, but a structural mismatch with the non-linear decision
    boundary. Reporting this honestly was important rather than tuning it
    further.
    \item \textbf{Cluster network access.} Pushing artefacts from
    \texttt{hadoop-01} to GitHub required a small workaround for DNS
    resolution of \texttt{github.com}, solved by an explicit
    \texttt{HostName} entry in \texttt{\textasciitilde/.ssh/config}.
\end{itemize}

\subsection{Recommendations}

\begin{enumerate}[leftmargin=2em]
    \item Replace the row-level random split with a group-aware split per
    \texttt{capture\_id} (Insight 4 motivates this directly).
    \item Add Gradient-Boosted Trees to the model grid; they should
    out-perform Random Forest on this kind of categorical-heavy feature
    space.
    \item Stream a copy of the same Hive partitions into Spark Structured
    Streaming and serve the trained Random Forest as a near-real-time
    classifier.
    \item Extend the dashboard with per-class precision/recall and a
    confusion-matrix heatmap --- the current panel summarises overall
    metrics only.
\end{enumerate}
